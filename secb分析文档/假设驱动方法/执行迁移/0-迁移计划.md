  建议路线

  - 先抽象出一个“SanitizerReportAnalyzer”模块，从崩溃日志/asan 输出生成结构化事实、候选 root cause 表和待验证问题清单，直接复用你文档
  中 Round0 的关键产物（候选表、开放疑问、关键帧）VulnTree/docs/系统架构/重构系统架构文档.md:169。
  - 基于 SWE-agent 的配置系统，新建一个轻量的 HypothesisState（active/pending/refuted 等字段 + open_questions + evidence）结构，放在
  自定义 hook 或 history_processor 中维护，每轮提示把当前假设视图拼入模板，类似你计划视图的最小化版 VulnTree/docs/系统架构/重构系统架
  构文档.md:34。
  - 让模型通过一个固定的 JSON 工具（等价于简单版 UpdatePlan）汇报：hypothesis_update、new_questions、support/contradiction。解析后更
  新 HypothesisState，并在需要切换时设置显式标志。
  - 切换流程优先做成“显式信号 + 深度优先继续”的最小骨架：当收到 found_contradiction 时，把当前假设标为 refuted，选下一条 pending 假
  设，清空对话上下文里与旧假设直接绑定的提示，保留公共事实，用 SWE-agent 提供的 history_processor 控制上下文隔离。此流程直接对应你
  v3.11 的显式切换信号 VulnTree/docs/系统架构/重构系统架构文档.md:405。
  - 若之后需要扩展，再考虑把死胡同检测、LLM 辅助切换等高阶机制增量接回 VulnTree/docs/系统架构/重构系统架构文档.md:444。

  工作量评估

  - Sanitizer 抽象层：实现解析 + 结构体输出 + 模板注入，大约 1–2 人天（取决于日志格式复杂度）。
  - Hypothesis 管理（数据结构、Hook、提示改写、JSON 工具定义）：约 3–5 人天，需要多次提示调参。
  - 上下文隔离（history_processor + 储存多版本事实 + prompt 选择）：2–4 人天，主要时间花在如何既保留通用语境又避免旧假设噪声。
  - 如需进一步引入死胡同检测或 MCTS 评分，再额外预留至少一周。

  可行性判断

  - 假设跟踪与更新：在 SWE-agent 里完全可行。Agent 模板天然支持插入结构化块，工具链也允许定义“更新”类动作，因此只需要编写解析逻辑和提
  示规范即可，难点主要在提示收敛而非工程阻碍。
  - 假设切换后的上下文隔离：需要在 SWE-agent 的对话历史中做“局部 reset”。可以把每条假设的历史片段拆分成一个 memory buffer，切换时仅回
  放公共事实 + 当前假设片段，利用 CombinedAgentHook 或自定义 history_processor 截断其余部分。实现难度中等，但和框架契合度高。
